# Правила работы AI-агента над проектом

## 1. Обязательные документы

Перед началом работы агент должен учитывать:

- `docs/product_spec.md`
- `docs/architecture.md`
- `docs/implementation_plan.md`
- `docs/project_state.md`
- `docs/design.md`

### Приоритет документов
Если есть конфликт:
1. `product_spec.md`
2. `architecture.md`
3. `implementation_plan.md`
4. `project_state.md`
5. `design.md`

Если конфликт критичный — не придумывать новое архитектурное решение без запроса.

---

## 2. Учитывать доступные skills и инструменты

В рабочем окружении доступны:
- Flutter skills
- Pontail / Poniteil skills, если они применяются агентом автоматически
- Graphify
- Context7

Агент должен использовать их уместно.

### Context7
Использовать для проверки актуальной документации и API:
- Flutter
- Riverpod
- go_router
- Drift
- SharedPreferences
- flutter_local_notifications
- RuStore Billing
- Яндекс Mobile Ads

### Graphify
**Graphify** — это внешний инструмент (https://github.com/safishamsi/graphify), который строит граф знаний из кода и документации проекта. Установлен на машине разработчика (`graphify --version` → 0.8.38). Cursor-правило для проекта — `.cursor/rules/graphify.mdc` (уже установлено).

Использовать после завершения крупных этапов:
```
graphify .
```
Это создаёт `graphify-out/graph.html`, `graphify-out/GRAPH_REPORT.md`, `graphify-out/graph.json`.

Для запроса к графу:
```
graphify query "вопрос об архитектуре"
```

После запуска обновлять:
- `docs/project_state.md`

**Не путать с Canvas** — Canvas это встроенный инструмент Cursor для интерактивных React-дашбордов. Graphify и Canvas — разные инструменты.

---

## 3. Ограничение области изменений

Агент должен реализовывать только текущий этап или подэтап из:
- `docs/implementation_plan.md`

Не нужно:
- трогать несвязанные файлы
- переписывать уже рабочие модули без причины
- менять архитектуру без запроса
- добавлять новые крупные зависимости без необходимости

---

## 4. Не тратить токены на предварительные планы

Агенту не нужно перед каждым изменением писать длинный план действий.

Допустимо:
- сразу выполнять задачу
- после выполнения дать короткий отчёт
- обновить документы состояния

---

## 5. После завершения этапа

После завершения этапа или крупного подэтапа агент обязан:

1. Отметить выполненные чекбоксы в `docs/implementation_plan.md`
2. Обновить `docs/project_state.md`
3. При необходимости сделать Graphify / структурную сводку
4. Дать короткий отчёт:
   - что сделано
   - какие файлы изменены
   - что осталось
   - есть ли проблемы или долги

---

## 6. Базовые архитектурные правила

Использовать:
- Flutter
- Riverpod
- go_router
- Drift / SQLite
- SharedPreferences
- feature-first
- прагматичную Clean Architecture
- Material 3 + Notion-style

Не использовать:
- Bloc как основной state management
- Provider как основной state management
- get_it
- Firebase
- Google Analytics
- Google Sign-In
- серверы
- облачную синхронизацию
- Google Play Billing
- Google Mobile Ads вместо Яндекс рекламы
- Interstitial / AppOpen / Rewarded рекламу

---

## 7. Правила по слоям

### UI не должен
- выполнять SQL
- напрямую обращаться к SDK рекламы
- напрямую обращаться к SDK биллинга
- напрямую обращаться к notification plugin
- считать тяжёлую статистику и streak rules

### Domain должен
- считать серии
- считать expected days
- считать статистику
- обрабатывать repeat rules
- содержать чистую бизнес-логику

### Data должен
- работать с Drift
- маппить database rows в domain-модели
- реализовывать репозитории

---

## 8. Правила по БД

- использовать Drift
- хранить только явные действия пользователя в `habit_entries`
- не генерировать пустые записи на каждый день заранее
- отсутствие записи в прошлом ожидаемом дне трактовать на уровне бизнес-логики
- настройки хранить в SharedPreferences

---

## 9. Правила по уведомлениям

Уведомления должны идти через отдельный модуль:
- `features/notifications`

Нельзя размазывать логику уведомлений по UI.

Все пересчёты расписания уведомлений должны идти через `NotificationScheduler` / `NotificationOrchestrator`.

---

## 10. Правила по монетизации

Premium и Ads должны быть изолированы в:
- `features/monetization`

UI работает только через провайдеры / абстракции.

Нельзя напрямую использовать SDK рекламы или биллинга внутри экранов.

---

## 11. Правила по дизайну

Использовать:
- `docs/design.md`

Дизайн-направление:
- Notion-style
- warm minimalism
- soft surfaces
- rounded cards
- light theme first
- calendar-first UI
- спокойные цвета

Не делать:
- dark-first как основное направление
- glassmorphism
- кислотные градиенты
- перегруженные анимации
- тяжёлый enterprise dashboard

---

## 12. Правила по `project_state.md`

`docs/project_state.md` должен быть:
- коротким
- актуальным
- практичным

Не нужно копировать туда всё ТЗ.

Нужно фиксировать:
- что уже готово
- какие пакеты используются
- какие модули завершены
- ключевые решения
- известные долги
- следующий этап
